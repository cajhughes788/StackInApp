# Plaid Bank Integration — Architecture

This document is a handoff for the Plaid bank-linking feature: linking a bank account, getting push-notified on new transactions, and reviewing a rule-based business/personal + category guess before it becomes a real expense.

## Product Context

A user links a bank account via Plaid Link from Account Settings. From then on, every new transaction on that account:

1. Triggers a push notification.
2. Gets a category + business-vs-personal guess, shown on the Expenses tab (home screen) for the user to confirm or dismiss — it never becomes a real expense automatically.
3. That confirm/dismiss decision is remembered per merchant, so the same merchant is classified correctly (and, if dismissed once, doesn't keep re-asking) on every future transaction — see Merchant memory below.

This mirrors the existing CSV/Venmo import convention (`shared/schemas/import.ts`, `frontend/lib/imports/csvImportParsers.ts`): the app suggests, the user confirms.

## Architecture

### Data model

Three new collections/schemas:

- [shared/schemas/plaidItem.ts](/Users/cajetanhughes/Desktop/App/TrackdOptimized/shared/schemas/plaidItem.ts) — `workspaces/{workspaceId}/plaidItems/{itemId}` (doc id = Plaid's `item_id`). Holds the Plaid access token (`accessTokenEncrypted` — currently stored as the raw token; see Known Follow-Ups), sync cursor, linked accounts, and `linkOwnerUid` (whoever ran Link, used to target push notifications). `PlaidItemPublicSchema` omits the token for anything returned to the client.
- [shared/schemas/plaidPendingTransaction.ts](/Users/cajetanhughes/Desktop/App/TrackdOptimized/shared/schemas/plaidPendingTransaction.ts) — `workspaces/{workspaceId}/plaidPendingTransactions/{plaidTransactionId}`. One per unconfirmed transaction; doc id = Plaid's `transaction_id` so webhook replays are idempotent merge-writes, not queries.
- [shared/schemas/deviceToken.ts](/Users/cajetanhughes/Desktop/App/TrackdOptimized/shared/schemas/deviceToken.ts) — `users/{uid}/deviceTokens/{fcmToken}`. User-scoped like `users/{uid}/subscription/current`.
- A top-level `plaidItemIndex/{itemId} -> { workspaceId }` collection (no schema file, written inline in `plaidService.ts`) lets the webhook handler — which only receives a Plaid `item_id`, no workspace context — find the owning workspace in one read instead of a Firestore collection-group query (which would need its own composite index).
- [shared/schemas/plaidMerchantMemory.ts](/Users/cajetanhughes/Desktop/App/TrackdOptimized/shared/schemas/plaidMerchantMemory.ts) — `workspaces/{workspaceId}/plaidMerchantMemory/{merchantKey}`. One per distinct merchant the user has confirmed or dismissed at least once (`isBusiness`, `expenseCategory`, `decisionCount`). `merchantKey` comes from `normalizePlaidMerchantKey()` in `shared/plaidClassification.ts` (lowercased, punctuation and store-number digits stripped, so "Target 1147" and "Target 2203" collapse to one entry).

**Security rule fix**: `firestore.rules`'s existing `workspaces/{workspaceId}/{document=**}` wildcard grants read to any workspace member for every subcollection, which would have exposed raw Plaid access tokens to any client-side Firestore read. Added an explicit `plaidItems/{itemId} { allow read: if false }` override. All Plaid data is read via backend routes, like everything else in this app, so this costs nothing functionally.

### Backend

Follows the Stripe integration's shape exactly:

- [backend/functions/src/secrets.ts](/Users/cajetanhughes/Desktop/App/TrackdOptimized/backend/functions/src/secrets.ts) — `PLAID_CLIENT_ID`, `PLAID_SECRET`, `PLAID_ENV`.
- [backend/functions/src/services/plaidService.ts](/Users/cajetanhughes/Desktop/App/TrackdOptimized/backend/functions/src/services/plaidService.ts) — all Plaid API calls and Firestore writes: `createLinkToken`, `exchangePublicToken`, `getItems`, `unlinkItem`, `syncTransactionsForItem`, `importPlaidHistory`, `getPendingTransactions`, `confirmPendingTransaction` (calls the *existing* `expensesService.createExpense` with `clientMutationId: "plaid:{transaction_id}"` so it inherits dedup/category-normalization/P&L-sync for free, and an optional `receiptAssetId`), `dismissPendingTransaction`.
- [backend/functions/src/routes/plaidWebhook.ts](/Users/cajetanhughes/Desktop/App/TrackdOptimized/backend/functions/src/routes/plaidWebhook.ts) — registered as a bare `onRequest` (not `withCorsAuth`) like `stripeWebhook.ts`, since it needs the raw body. Unlike Stripe's static-HMAC `constructEvent`, Plaid signs webhooks with a rotating ES256 key delivered as a JWT in the `Plaid-Verification` header — the handler decodes the JWT's `kid`, fetches/caches the matching key via `webhookVerificationKeyGet`, and verifies both the signature and a SHA-256 hash of the raw body. On a `TRANSACTIONS` / `SYNC_UPDATES_AVAILABLE` event it calls `syncTransactionsForItem`.
- [backend/functions/src/services/pushNotificationService.ts](/Users/cajetanhughes/Desktop/App/TrackdOptimized/backend/functions/src/services/pushNotificationService.ts) — thin wrapper over `admin.messaging()` (newly exported from `admin.ts`), called directly from `syncTransactionsForItem` after each new pending transaction (not via a Firestore trigger — the webhook handler already has the uid, so a trigger would just add a redundant read).
- Route files under `backend/functions/src/routes/` (`createPlaidLinkToken`, `exchangePlaidPublicToken`, `unlinkPlaidItem`, `getPlaidItems`, `getPlaidPendingTransactions`, `confirmPlaidPendingTransaction`, `importPlaidHistory`) plus `registerDeviceToken`, all wired into `api.ts` with the standard dynamic-import pattern.

### Bulk historical import

Live webhook detection lags — anywhere from Plaid's ~6-hour refresh cycle to multiple days depending on the institution, and some institutions (Capital One, notably) never report pending transactions at all, only posted ones. Two mechanisms cover this:

- **Ongoing sync** (`plaidWebhook` → `syncTransactionsForItem(itemId)`, no options): fires per Plaid's own `SYNC_UPDATES_AVAILABLE` webhook, notifies for each new transaction individually as it's detected. This is also what runs on the very first webhook right after linking — and that first call, same as a bulk import, would otherwise flood the user with a notification per transaction in their available history. `syncTransactionsForItem` detects this (`item.cursor == null` on entry) and treats it as silent automatically, same as an explicit bulk import.
- **`importPlaidHistory(workspaceId, uid, itemId, months = 3)`**: exposed as an **"Import last 3 months"** button per linked item in `plaid-connect-button.tsx`. Resets the item's cursor and re-runs sync bounded to a `sinceDate` cutoff, `silent: true` — transactions land straight in the pending-review list with no notification burst. Bounding to 3 months (configurable, capped at 24) matters for institutions with longer history than Capital One's 90-day window, where an unbounded pull could be hundreds of transactions at once.

Both paths funnel through the same `syncTransactionsForItem`, which now persists the sync cursor **after every page**, not just once the whole loop finishes — a multi-month backfill can span more Plaid pages than one function invocation's timeout allows, and without incremental persistence a mid-loop timeout forced the next attempt to redo all the same work from scratch (this is what made the first resync during testing take three tries before it succeeded). `importPlaidHistory` also runs with `timeoutSeconds: 300` (vs. the `withCorsAuth` default) for the same reason.

### Classification

- [shared/expenseKeywordMatching.ts](/Users/cajetanhughes/Desktop/App/TrackdOptimized/shared/expenseKeywordMatching.ts) — the keyword table that used to live only inside `frontend/lib/imports/csvImportParsers.ts`'s `expenseCategorySuggestion()`, extracted so the CSV importer and the Plaid classifier share one list. `csvImportParsers.ts` now imports `suggestExpenseCategoryFromText` from here.
- [shared/plaidClassification.ts](/Users/cajetanhughes/Desktop/App/TrackdOptimized/shared/plaidClassification.ts) — `classifyPlaidTransaction()`. First tries Plaid's Personal Finance Category (primary tier) against a static map to `EXPENSE_CATEGORY_GUIDE` labels; falls back to the shared keyword matcher. `isBusinessGuess` stays `null` unless a category is confident enough to imply business use on its own (rent/utilities, transportation, loan payments, bank fees) — a wrong confident guess is worse than an honest "not sure."

**Merchant memory (learns from confirm/dismiss)**: before running the generic classifier above, `createPendingTransactionFromPlaid` in `plaidService.ts` checks `plaidMerchantMemory` for this merchant first (via `getMerchantMemory`) and uses that decision at 0.95 confidence if present, skipping the generic guess entirely. `confirmPendingTransaction` writes to that memory on every decision (`rememberMerchantDecision`) — confirming a merchant remembers its category for next time; dismissing remembers it as not-business, so a recurring personal charge (daily coffee, etc.) stops generating a fresh notification+prompt every single time. This is per-workspace, not per-device — unlike the pre-existing `useExpenseMemoryStore` (frontend, localStorage-only, vendor→category for manual entry autofill), which this does not share state with.

### iOS native changes

- **FCM token bridging**: `@capacitor/push-notifications` only ever exposes the raw APNs device token on iOS — `admin.messaging()` on the backend needs an FCM registration token instead. `AppDelegate.swift` calls `FirebaseApp.configure()` and sets `Messaging.messaging().apnsToken` from the APNs token, which triggers Firebase to mint an FCM token; a small custom plugin, [frontend/ios/App/App/FcmTokenPlugin.swift](/Users/cajetanhughes/Desktop/App/TrackdOptimized/frontend/ios/App/App/FcmTokenPlugin.swift) (same pattern as the pre-existing `NativeGeofencePlugin.swift`), forwards that token to JS, which is what `registerPush.ts` actually sends to `registerDeviceToken`. `Podfile` — added `Firebase/Messaging`, deliberately placed in the `target 'App' do` block rather than inside the `capacitor_pods` function, since `npx cap sync` regenerates that function from installed `@capacitor/*` plugins and silently drops anything non-Capacitor added inside it.
- **Notification delegate**: `AppDelegate.swift` does **not** set `UNUserNotificationCenter.current().delegate` — Capacitor's own bridge (`CapacitorBridge.swift`'s `NotificationRouter`) claims that slot itself and routes `willPresent`/`didReceive` into both `@capacitor/push-notifications` and `@capacitor/local-notifications`'s JS listeners. The app previously assigned `AppDelegate` as the delegate itself, which silently blocked tap events for *both* plugins (this predates the Plaid work — local-notification taps never fired either). `capacitor.config.ts`'s `PushNotifications.presentationOptions` (`["badge","sound","alert"]`) is required to keep foreground push banners showing once Capacitor owns the delegate — without it, `PushNotificationsHandler.willPresent` returns no presentation options by default.
- `frontend/ios/App/App/App.entitlements` (new) — `aps-environment: production`, wired into both build configs via `CODE_SIGN_ENTITLEMENTS` in `project.pbxproj`.
- `Info.plist` — added `remote-notification` to `UIBackgroundModes`.
- `frontend/ios/App/App/GoogleService-Info.plist` — registered as an iOS app in the Firebase console and bundled as a built resource (`PBXResourcesBuildPhase`), required for `FirebaseApp.configure()`.

## Scope Decisions

- **Suggest-and-confirm, not auto-create.** Explicitly chosen over auto-creating expenses, to match the CSV-import precedent and avoid silently misclassifying personal spending as business.
- **Rule-based classification only.** No LLM. Confirmed with the user as a deliberate v1 scope cut.
- **iOS push only.** Android FCM setup (`google-services.json`, manifest changes) is additive later — the backend push service is already platform-agnostic.
- **No `ITEM_LOGIN_REQUIRED` re-auth flow.** An item that errors just shows `status: "error"`; a re-link UI is a follow-up.

## Known Follow-Ups

- **Access token encryption at rest.** `accessTokenEncrypted` currently stores the plaintext Plaid access token. Firestore rules block all client reads of `plaidItems` (see above), so this isn't client-exposed, but there's no application-layer encryption (e.g. Cloud KMS envelope encryption) yet — worth adding before scaling past a trial.
- **Android push notifications.**
- **LLM-assisted classification** for transactions neither the merchant memory nor the rule-based classifier can confidently categorize.
- **No UI to view/edit/reset learned merchants.** `plaidMerchantMemory` is written and read automatically, but there's no settings screen listing what's been learned or letting a user correct/forget a bad memory (e.g. if they confirm a merchant under the wrong category once by mistake, every future transaction from that merchant will keep suggesting the wrong category until a raw Firestore edit or a UI for this gets built).
- **`ITEM_LOGIN_REQUIRED` re-link flow.** An errored item just shows "Connection needs attention" with an Unlink button — no in-place reconnect. See evaluation below; this gets more important as more accounts are linked.
- **Plaid product/pricing tier review** before moving off the trial key — see the app's own cost discussion; Transactions is billed per linked Item per month.
- **Bulk review actions.** Now that `importPlaidHistory` can land dozens of transactions at once, confirming or dismissing them one-by-one is tedious. See evaluation below.
- **Per-account business/personal default.** A linked Item can have multiple `linkedAccounts` (e.g. one Item with both a personal and a business checking account). Classification is currently per-transaction only, with no way to bias the guess by which account it came from.
- **Vehicle-expense mode isn't reachable from Plaid.** `confirmPendingTransaction` always calls `createExpense` with the default (manual) calculation method — a gig driver's fuel purchase gets confirmed as a flat-amount expense, never routed through the existing mileage-based vehicle expense calculator that `ExpenseForm` already has.

## Practical Use-Case Evaluation — Business Owners & Gig Workers

Requested review of whether the current design holds up for real day-to-day use, beyond the happy path already built. Ranked roughly by impact.

1. **Bulk review is the biggest immediate gap.** A gig worker who links an account with 3 months of history, or a business owner who hasn't opened the app in two weeks, now lands on a list of dozens of transactions (mitigated from a notification-flood standpoint by the silent-import work above, but not from a review-effort standpoint). Confirming each one individually — select category, tap confirm, repeat — doesn't scale. **Recommendation:** multi-select with a bulk "confirm all as [category]" / "dismiss all" action, at minimum for transactions sharing a suggested category or merchant.
2. **Business bank accounts vs. personal bank accounts.** Many gig workers and small business owners keep a dedicated checking account or card for the business, but nothing here lets the user say "everything from this specific linked account defaults to business" — every transaction still goes through the same generic classifier regardless of which account it came from. This is a relatively small addition (a flag on `linkedAccounts` entries, checked before the keyword/PFC classifier) with outsized accuracy improvement for exactly this user.
3. **Mileage-based vehicle expenses don't connect to Plaid at all.** Rideshare/delivery drivers are a core "gig worker" case, and `ExpenseForm` already has a whole mileage-vs-actual-expense mode for this (`vehicleExpenseMode`, `businessMiles`, `mileageRate`). A gas station or toll charge coming in through Plaid gets none of that — it becomes a flat manual expense. Actual fuel cost is a legitimate deduction in its own right, so this isn't broken, but it means a driver using the standard mileage method (the more common, simpler method) gets fuel purchases from Plaid double-counted or miscategorized if not careful. Worth at minimum flagging fuel/parking/toll categories at confirm time and asking which method applies.
4. **Recurring subscriptions aren't tied to the existing recurring-rules feature.** The app already has `recurringRules` (auto-generates expenses on a cadence). A Plaid-detected SaaS subscription (common deductible expense for both business owners and gig workers — accounting software, delivery-platform fees, etc.) is currently treated as a one-off transaction every time it recurs, re-asking the same classification question monthly instead of being offered "this looks recurring — turn it into a recurring rule?" after 2-3 confirmed occurrences from the same merchant at a similar amount.
5. **Reconnection matters more than the current follow-up note suggests.** A stale/expired bank credential (`ITEM_LOGIN_REQUIRED`) means silent data loss — no new transactions, no notification that anything is wrong beyond a small "Connection needs attention" label the user has to notice on a settings page they don't visit often. For someone relying on this to catch every business expense, an expired connection failing silently for weeks is a real risk to their tax records. This should be promoted above "nice to have" — at minimum, a periodic check that flags stale items with a push notification of its own ("Reconnect your bank — StackIn hasn't seen new transactions in 2 weeks").
6. **Receipt requirement gaps for audit defense.** Now that receipt attach exists for Plaid-confirmed expenses (see above), the natural follow-up is IRS documentation completeness — expenses over $75 generally need a receipt for audit defense in the US. Nothing currently flags "this confirmed Plaid expense has no receipt and is over $75" the way, say, a review dashboard might. Not urgent, but worth a lightweight badge/filter in the expenses grid.
7. **What's already solid for this audience:** the merchant-memory design (mixed-use merchants like the Walmart example don't get silently and permanently misclassified), the fact that Plaid-confirmed expenses flow through the exact same `createExpense` path as manual/CSV/receipt-OCR expenses (so P&L, tax profile, and reporting all already include them with no separate code path), and per-item multi-account support (a user isn't limited to one linked account).

## How to Verify End-to-End

1. `cd backend/functions && npm install && npm run build` — confirms the new routes/services compile.
2. `cd frontend && npm install` — pulls in `react-plaid-link` and `@capacitor/push-notifications`.
3. `cd frontend/ios/App && pod install` — installs the new `CapacitorPushNotifications` pod.
4. Set `PLAID_CLIENT_ID`, `PLAID_SECRET`, `PLAID_ENV` as Firebase secrets (`firebase functions:secrets:set PLAID_CLIENT_ID`, etc.) and configure the Plaid dashboard's webhook URL to point at the deployed `plaidWebhook` function.
5. From the iOS simulator or a device build, open Account Settings → Connect a bank → complete Plaid Link (sandbox or production) → confirm a `plaidItems` doc appears in Firestore with no access token visible via any client-facing response.
6. Fire a test transaction webhook from the Plaid dashboard → confirm a `plaidPendingTransactions` doc appears with a sensible suggestion, and a push notification arrives on a registered device.
7. Tap Confirm → a real `Expense` shows up in `frontend/app/app/profitloss/page.tsx`'s P&L view, and a repeated webhook delivery does not create a duplicate (idempotent via `clientMutationId`).
8. Tap Dismiss on another pending transaction → confirm no expense is created.
9. Tap "Import last 3 months" on a linked item → confirm transactions land in the pending list with **no** push notification burst, and that the review list auto-collapses if there are more than 5.
10. Attach a receipt photo via the paperclip button on a pending row, then confirm as business → confirm the resulting expense has a `receiptAssetId` and the photo is viewable from the expenses grid.
